# Протокол P2P Overlay Network

## 1. Общая информация

Проект использует собственный прикладной протокол поверх TCP.

TCP обеспечивает надёжный упорядоченный поток байтов, однако не сохраняет
границы сообщений. Поэтому поверх TCP используется собственный формат кадра
(Frame).

Текущая версия протокола:

PROTOCOL_VERSION = 1

Максимальный размер полезной нагрузки по умолчанию:

MAX_FRAME_PAYLOAD = 65536 байт

Параметры версии протокола и максимального размера payload задаются
конфигурацией узла.

На этапе 1 реализованы:

- TCP-сервер и исходящие TCP-соединения;
- собственный формат кадра;
- потоковый декодер;
- сериализация MessagePack;
- PING/PONG RPC;
- сообщение ERROR;
- проверка направления сообщений;
- проверка request_id;
- обработка основных ошибок протокола.


## 2. Формат кадра

Каждое сообщение передаётся в виде:

[ HEADER ][ PAYLOAD ]

Заголовок имеет фиксированный размер 24 байта.

Все многобайтовые целые значения передаются в сетевом порядке байтов
(Big Endian).

### 2.1. Структура заголовка

| Поле | Смещение | Размер | Назначение |
|---|---:|---:|---|
| version | 0 | 1 байт | Версия протокола |
| type | 1 | 1 байт | Тип сообщения |
| flags | 2 | 2 байта | Флаги |
| request_id | 4 | 16 байт | Идентификатор RPC |
| payload_length | 20 | 4 байта | Размер payload |
| payload | 24 | переменный | Полезная нагрузка |

Итого фиксированный заголовок:

24 байта.

В Python структура кодируется форматом:

!BBH16sI

где:

- ! — сетевой порядок байтов (Big Endian);
- B — unsigned char, 1 байт;
- B — unsigned char, 1 байт;
- H — unsigned short, 2 байта;
- 16s — последовательность из 16 байт;
- I — unsigned int, 4 байта.


## 3. Типы и направления сообщений

В протоколе определены следующие типы:

| Код | Название | Направление |
|---:|---|---|
| 0x01 | PING | request |
| 0x02 | PONG | response |
| 0x7F | ERROR | response / notification |

На этапе 1 используются PING, PONG и ERROR.

Получение сообщения в недопустимом направлении является ошибкой протокола.

Например, если сторона, ожидающая запрос, получает PONG в качестве нового
запроса, она формирует ERROR с кодом INVALID_DIRECTION.


## 4. request_id

Каждый RPC-запрос содержит 16-байтовый request_id.

Для нового запроса идентификатор генерируется криптографически стойким
генератором случайных данных:

secrets.token_bytes(16)

Ответ на запрос обязан содержать тот же request_id.

Пример:

PING:
request_id = A1B2...

PONG:
request_id = A1B2...

Если request_id ответа не соответствует request_id ожидаемого запроса,
ответ отклоняется.

request_id используется для корреляции RPC-запроса и соответствующего ответа.


## 5. Сериализация Payload

Payload сериализуется в формате MessagePack.

Используется библиотека msgpack.

Общая схема:

Python dict
    |
    v
MessagePack encoder
    |
    v
bytes
    |
    v
Frame payload

На принимающей стороне выполняется обратная операция.

После декодирования обязательно проверяются:

- тип корневого объекта;
- набор обязательных полей;
- отсутствие неизвестных полей;
- тип каждого значения;
- диапазоны числовых значений;
- допустимые размеры строк и бинарных полей.

Неизвестные поля отклоняются, если иное явно не предусмотрено версией
протокола.


## 6. Почему выбран MessagePack

Для проекта рассматривались JSON, MessagePack и Protocol Buffers.

### JSON

Преимущества:

- простой;
- человекочитаемый;
- широко поддерживается.

Недостатки:

- текстовый формат;
- больший размер сообщений;
- бинарные данные требуют дополнительного представления.

### MessagePack

Преимущества:

- бинарный формат;
- компактнее JSON;
- непосредственно поддерживает bytes;
- не требует отдельной схемы компиляции;
- хорошо подходит для собственного учебного протокола.

Недостатки:

- payload нельзя непосредственно прочитать как текст;
- требуется внешняя библиотека;
- строгая схема должна контролироваться приложением.

### Protocol Buffers

Преимущества:

- строгая схема;
- компактный бинарный формат;
- высокая производительность.

Недостатки:

- требуется отдельное описание схемы;
- появляется дополнительный этап генерации/сопровождения схем;
- для данного прототипа добавляет инфраструктуру, не связанную напрямую
  с изучением собственного протокола.

Для проекта выбран MessagePack как компромисс между компактностью,
поддержкой бинарных данных и простотой реализации.

Строгость протокола обеспечивается собственным уровнем валидации после
десериализации.


## 7. Contact

Сообщения протокола могут содержать описание P2P-узла — Contact.

Логическая модель Contact:

{
    "node_id": bytes,
    "identity_algorithm": string,
    "identity_public_key": bytes,
    "host": string,
    "port": uint16
}

Поля:

- node_id — идентификатор P2P-узла;
- identity_algorithm — название алгоритма идентификации;
- identity_public_key — публичный ключ узла;
- host — сетевой адрес узла;
- port — TCP-порт узла.

Локальные метаданные маршрутизации, такие как last_seen_ms и
last_verified_ms, по сети не передаются. Они должны устанавливаться локально
после получения и проверки контакта.

### Contact на этапе 1

На этапе 1 криптографическая идентичность узла ещё не реализуется.

Поэтому временно используются:

node_id = b""
identity_algorithm = "stage1-none"
identity_public_key = b""

Это осознанное ограничение этапа 1, а не окончательный формат идентичности.


Сетевые поля host и port используются уже на этапе 1.


## 8. PING

PING используется для проверки доступности другого узла.

Тип сообщения:

0x01

Направление:

request

Payload:

{
    "sender": Contact,
    "timestamp_ms": uint64
}

sender содержит сетевое описание отправителя.

timestamp_ms содержит временную метку отправки PING в миллисекундах.

Допустимый диапазон:

0 <= timestamp_ms <= 2^64 - 1

При получении PING:

1. payload десериализуется;
2. проверяется точный набор полей;
3. проверяется Contact отправителя;
4. проверяется timestamp_ms;
5. Dispatcher передаёт запрос обработчику PING;
6. формируется PONG с тем же request_id.


## 9. PONG

Тип сообщения:

0x02

Направление:

response

Payload:

{
    "responder": Contact,
    "ping_timestamp_ms": uint64,
    "responder_timestamp_ms": uint64
}

Поля:

- responder — Contact узла, сформировавшего ответ;
- ping_timestamp_ms — timestamp_ms из исходного PING;
- responder_timestamp_ms — временная метка формирования PONG.

PONG обязан использовать request_id соответствующего PING.

Инициатор проверяет:

- тип ответа;
- request_id;
- структуру PONG;
- типы и диапазоны полей;
- совпадение ping_timestamp_ms с timestamp исходного PING.

RTT измеряется локально как время между отправкой PING и получением
корректного PONG.

## 12. ERROR

Тип сообщения:

0x7F

Направление:

response / notification

Payload:

{
    "code": string,
    "message": string
}

На этапе 1 размер code ограничивается 64 символами, а message —
256 символами.

Примеры кодов:

INVALID_PAYLOAD
INVALID_DIRECTION
NOT_IMPLEMENTED
UNSUPPORTED_MESSAGE

ERROR должен использовать request_id исходного сообщения, если этот
идентификатор удалось корректно получить.

Текст ERROR не должен содержать:

- traceback;
- пути файловой системы;
- закрытые ключи;
- секретные данные;
- неограниченные данные, полученные от удалённого узла.

При ошибке payload удалённой стороне передаётся контролируемое сообщение,
например:

{
    "code": "INVALID_PAYLOAD",
    "message": "Payload validation failed"
}

а не исходный текст внутреннего исключения.


## 11. Работа с TCP-потоком

TCP является потоковым протоколом и не сохраняет границы сообщений.

Поэтому запрещено считать, что один вызов read() соответствует одному Frame.

В одном чтении может находиться:

- часть заголовка;
- заголовок и часть payload;
- один полный Frame;
- несколько Frame одновременно.

Для обработки используется StreamDecoder с внутренним буфером.

StreamDecoder:

1. накапливает данные до получения полного 24-байтового заголовка;
2. декодирует заголовок;
3. проверяет версию, тип и payload_length;
4. ожидает необходимое количество байтов payload;
5. формирует Frame;
6. продолжает обработку оставшихся байтов.

Таким образом, корректность протокола не зависит от того, каким образом
операционная система разбила TCP-поток на отдельные чтения.


## 12. Ограничение размера

До ожидания полного payload проверяется:

payload_length <= max_frame_payload

Значение по умолчанию:

max_frame_payload = 65536

Если:

payload_length > max_frame_payload

кадр отклоняется до ожидания или выделения памяти под заявленный payload.

Это защищает узел от неконтролируемого потребления памяти из-за чрезмерного
значения payload_length.


## 13. Обработка ошибок протокола

Нарушениями протокола считаются:

- неподдерживаемая версия;
- неизвестный тип сообщения;
- payload_length больше допустимого;
- некорректный MessagePack;
- несоответствие payload ожидаемой схеме;
- неизвестные поля;
- недопустимое направление сообщения;
- неправильный request_id ответа;
- обрыв TCP-соединения посреди заголовка или payload.

Ошибка отдельного соединения не должна останавливать TCP-сервер или весь
P2P-узел.

Если заголовок не может быть безопасно интерпретирован, соединение
закрывается без попытки сформировать ответ.

Если корректный Frame уже получен, но ошибка обнаружена на уровне payload
или направления сообщения, узел по возможности формирует ERROR.

После ошибки состояние конкретного соединения освобождается.


## 14. PING/PONG RPC

Последовательность обмена:

Node A                              Node B

   |                                  |
   | -------- PING -----------------> |
   |      request_id = X              |
   |      sender = Contact A           |
   |      timestamp_ms = T1            |
   |                                  |
   |                              Dispatcher
   |                                  |
   | <-------- PONG ----------------- |
   |      request_id = X              |
   |      responder = Contact B        |
   |      ping_timestamp_ms = T1       |
   |      responder_timestamp_ms = T2  |
   |                                  |

На этапе 1 для одного RPC используется отдельное TCP-соединение.

После получения ответа клиентская сторона закрывает соединение.

Такое решение упрощает:

- корреляцию запросов и ответов;
- управление временем ожидания;
- обработку ошибок соединения;
- реализацию первого этапа.



## 15. Проверка реализации этапа 1

Реализация этапа 1 проверяется автоматическими и ручными тестами.

Автоматически проверяются:

- encode/decode кадра;
- фиксированный заголовок размером 24 байта;
- частичный заголовок;
- частичный payload;
- несколько кадров в одном TCP-потоке;
- 100 кадров со случайной фрагментацией;
- превышение MAX_FRAME_PAYLOAD;
- неизвестная версия;
- неизвестный тип сообщения;
- обрыв соединения внутри кадра;
- некорректный request_id;
- некорректный MessagePack;
- несоответствие payload схеме;
- PING/PONG;
- ERROR;
- недопустимое направление сообщения;
- сохранение работоспособности сервера после ошибки клиента.

На момент завершения этапа 1 набор автоматических тестов содержит
33 успешно проходящих теста.

Дополнительно выполнен ручной сценарий с двумя независимыми процессами:

Node1:
127.0.0.1:9101

Node2:
127.0.0.1:9102

Node2 устанавливает соединение с Node1 как с bootstrap-узлом, отправляет
PING и получает корректный PONG с тем же request_id.

Дополнительно утилита scripts/send_ping.py позволяет вручную отправить
PING работающему узлу:

python scripts/send_ping.py --host 127.0.0.1 --port 9101

Успешный ответ содержит PONG и тот же request_id.
