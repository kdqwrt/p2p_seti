# Протокол P2P Overlay Network

## 1. Общая информация

Проект использует собственный прикладной протокол поверх TCP.

TCP обеспечивает надёжный упорядоченный поток байтов, однако не сохраняет
границы сообщений. Поэтому поверх TCP используется собственный формат кадра
(Frame).

Текущая версия протокола:

PROTOCOL_VERSION = 1

Максимальный размер полезной нагрузки по умолчанию:

MAX_FRAME_PAYLOAD = 65536 байт

Параметры версии протокола и максимального размера payload задаются
конфигурацией узла.

На этапе 1 реализованы:

- TCP-сервер и исходящие TCP-соединения;
- собственный формат кадра;
- потоковый декодер;
- сериализация MessagePack;
- PING/PONG RPC;
- сообщение ERROR;
- проверка направления сообщений;
- проверка request_id;
- обработка основных ошибок протокола.


## 2. Формат кадра

Каждое сообщение передаётся в виде:

[ HEADER ][ PAYLOAD ]

Заголовок имеет фиксированный размер 24 байта.

Все многобайтовые целые значения передаются в сетевом порядке байтов
(Big Endian).

### 2.1. Структура заголовка

| Поле | Смещение | Размер | Назначение |
|---|---:|---:|---|
| version | 0 | 1 байт | Версия протокола |
| type | 1 | 1 байт | Тип сообщения |
| flags | 2 | 2 байта | Флаги |
| request_id | 4 | 16 байт | Идентификатор RPC |
| payload_length | 20 | 4 байта | Размер payload |
| payload | 24 | переменный | Полезная нагрузка |

Итого фиксированный заголовок:

24 байта.

В Python структура кодируется форматом:

!BBH16sI

где:

- ! — сетевой порядок байтов (Big Endian);
- B — unsigned char, 1 байт;
- B — unsigned char, 1 байт;
- H — unsigned short, 2 байта;
- 16s — последовательность из 16 байт;
- I — unsigned int, 4 байта.



## 3. Типы и направления сообщений

В протоколе используются запросы и ответы для проверки доступности узлов, поиска контактов и работы с распределённым хранилищем DHT.

Основные типы сообщений:

| Код | Название | Направление | Назначение |
|---|---|---|---|
| 0x01 | PING | request | Проверка доступности узла |
| 0x02 | PONG | response | Ответ на PING |
| 0x03 | FIND_NODE_REQUEST | request | Поиск ближайших узлов |
| 0x04 | FIND_NODE_RESPONSE | response | Возврат найденных контактов |
| 0x05 | STORE_REQUEST | request | Сохранение записи в DHT |
| 0x06 | STORE_RESPONSE | response | Подтверждение сохранения |
| 0x07 | FIND_VALUE_REQUEST | request | Поиск записи по DHT-ключу |
| 0x08 | FIND_VALUE_RESPONSE | response | Результат поиска записи |
| 0x7F | ERROR | response / notification | Сообщение об ошибке |

PING/PONG реализованы на этапе 1.

FIND_NODE_REQUEST и FIND_NODE_RESPONSE реализованы на этапе 2.

STORE_REQUEST, STORE_RESPONSE, FIND_VALUE_REQUEST и FIND_VALUE_RESPONSE реализованы на этапе 3.

Все перечисленные механизмы работают поверх Frame версии 1.

Каждый RPC-запрос содержит request_id, который должен совпадать с request_id соответствующего ответа.

Получение сообщения в недопустимом направлении считается ошибкой протокола.

Например, получение PONG в качестве нового входящего запроса приводит к ошибке INVALID_DIRECTION.

При ошибках валидации DHT-записей или нарушении правил версионирования операция отклоняется.

## 4. request_id

Каждый RPC-запрос содержит 16-байтовый request_id.

Для нового запроса идентификатор генерируется криптографически стойким
генератором случайных данных:

secrets.token_bytes(16)

Ответ на запрос обязан содержать тот же request_id.

Пример:

PING:
request_id = A1B2...

PONG:
request_id = A1B2...

Если request_id ответа не соответствует request_id ожидаемого запроса,
ответ отклоняется.

request_id используется для корреляции RPC-запроса и соответствующего ответа.


## 5. Сериализация Payload

Payload сериализуется в формате MessagePack.

Используется библиотека msgpack.

Общая схема:

Python dict
    |
    v
MessagePack encoder
    |
    v
bytes
    |
    v
Frame payload

На принимающей стороне выполняется обратная операция.

После декодирования обязательно проверяются:

- тип корневого объекта;
- набор обязательных полей;
- отсутствие неизвестных полей;
- тип каждого значения;
- диапазоны числовых значений;
- допустимые размеры строк и бинарных полей.

Неизвестные поля отклоняются, если иное явно не предусмотрено версией
протокола.


## 6. Почему выбран MessagePack

Для проекта рассматривались JSON, MessagePack и Protocol Buffers.

### JSON

Преимущества:

- простой;
- человекочитаемый;
- широко поддерживается.

Недостатки:

- текстовый формат;
- больший размер сообщений;
- бинарные данные требуют дополнительного представления.

### MessagePack

Преимущества:

- бинарный формат;
- компактнее JSON;
- непосредственно поддерживает bytes;
- не требует отдельной схемы компиляции;
- хорошо подходит для собственного учебного протокола.

Недостатки:

- payload нельзя непосредственно прочитать как текст;
- требуется внешняя библиотека;
- строгая схема должна контролироваться приложением.

### Protocol Buffers

Преимущества:

- строгая схема;
- компактный бинарный формат;
- высокая производительность.

Недостатки:

- требуется отдельное описание схемы;
- появляется дополнительный этап генерации/сопровождения схем;
- для данного прототипа добавляет инфраструктуру, не связанную напрямую
  с изучением собственного протокола.

Для проекта выбран MessagePack как компромисс между компактностью,
поддержкой бинарных данных и простотой реализации.

Строгость протокола обеспечивается собственным уровнем валидации после
десериализации.



## 7. Contact

Contact — структура, содержащая сведения о P2P-узле, необходимые для сетевого взаимодействия и маршрутизации.

Логическая модель Contact:

```python
{
    "node_id": bytes,
    "identity_algorithm": str,
    "identity_public_key": bytes,
    "host": str,
    "port": int
}
```

Назначение полей:

| Поле | Назначение |
|---|---|
| node_id | Идентификатор узла |
| identity_algorithm | Алгоритм криптографической идентификации |
| identity_public_key | Открытый ключ узла |
| host | IP-адрес узла |
| port | TCP-порт узла |

### 7.1. Криптографическая идентичность

Начиная с этапа 2, используется криптографическая идентичность на основе Ed25519.

Каждый узел имеет собственную пару ключей:

- закрытый ключ — хранится локально;
- открытый ключ — используется для проверки идентичности.

NodeID вычисляется на основе открытого ключа.

При проверке Contact контролируется соответствие NodeID открытому ключу.

Таким образом, идентификатор узла криптографически связан с его открытым ключом.

Закрытый ключ не передаётся другим узлам.

### 7.2. Проверка Contact

Перед использованием Contact выполняется проверка `validate_contact()`.

Проверяются структура, допустимые значения полей и согласованность криптографической идентичности.

Контакты используются в:

- PING/PONG;
- FIND_NODE;
- таблице маршрутизации;
- поиске ближайших узлов;
- операциях DHT.

При обнаружении нового узла выполняется проверка его доступности через PING.

После успешной проверки контакт может быть добавлен в таблицу маршрутизации.

### 7.3. Локальные метаданные

Такие сведения, как время последней проверки доступности, относятся к локальному состоянию таблицы маршрутизации.

Они не входят в передаваемую структуру Contact.

### 7.4. Историческое ограничение этапа 1

На этапе 1 криптографическая идентичность ещё не была реализована.

В первоначальном прототипе временно использовались пустые значения NodeID и открытого ключа.

Начиная с этапа 2, этот подход заменён криптографической идентичностью Ed25519.

Текущая реализация использует полноценные идентификаторы и открытые ключи узлов.


## 8. PING

PING используется для проверки доступности другого узла.

Тип сообщения:

0x01

Направление:

request

Payload:

{
    "sender": Contact,
    "timestamp_ms": uint64
}

sender содержит сетевое описание отправителя.

timestamp_ms содержит временную метку отправки PING в миллисекундах.

Допустимый диапазон:

0 <= timestamp_ms <= 2^64 - 1

При получении PING:

1. payload десериализуется;
2. проверяется точный набор полей;
3. проверяется Contact отправителя;
4. проверяется timestamp_ms;
5. Dispatcher передаёт запрос обработчику PING;
6. формируется PONG с тем же request_id.


## 9. PONG

Тип сообщения:

0x02

Направление:

response

Payload:

{
    "responder": Contact,
    "ping_timestamp_ms": uint64,
    "responder_timestamp_ms": uint64
}

Поля:

- responder — Contact узла, сформировавшего ответ;
- ping_timestamp_ms — timestamp_ms из исходного PING;
- responder_timestamp_ms — временная метка формирования PONG.

PONG обязан использовать request_id соответствующего PING.

Инициатор проверяет:

- тип ответа;
- request_id;
- структуру PONG;
- типы и диапазоны полей;
- совпадение ping_timestamp_ms с timestamp исходного PING.

RTT измеряется локально как время между отправкой PING и получением
корректного PONG.


## 10. ERROR


Тип сообщения:

0x7F

Направление:

response / notification

Payload:

{
    "code": string,
    "message": string
}

На этапе 1 размер code ограничивается 64 символами, а message —
256 символами.

Примеры кодов:

INVALID_PAYLOAD
INVALID_DIRECTION
NOT_IMPLEMENTED
UNSUPPORTED_MESSAGE

ERROR должен использовать request_id исходного сообщения, если этот
идентификатор удалось корректно получить.

Текст ERROR не должен содержать:

- traceback;
- пути файловой системы;
- закрытые ключи;
- секретные данные;
- неограниченные данные, полученные от удалённого узла.

При ошибке payload удалённой стороне передаётся контролируемое сообщение,
например:

{
    "code": "INVALID_PAYLOAD",
    "message": "Payload validation failed"
}

а не исходный текст внутреннего исключения.


## 11. FIND_NODE_REQUEST

FIND_NODE_REQUEST используется для поиска контактов узлов, идентификаторы которых наиболее близки к заданному идентификатору по метрике XOR.

Механизм реализован на этапе 2.

Направление сообщения: request.

Логическая структура payload:

```python
{
    "sender": Contact,
    "target_node_id": bytes
}
```

Поля:

- `sender` — контакт отправителя запроса;
- `target_node_id` — 32-байтовый идентификатор цели поиска.

При получении FIND_NODE_REQUEST узел:

1. Декодирует payload.
2. Проверяет структуру запроса.
3. Проверяет Contact отправителя.
4. Проверяет длину target_node_id.
5. Обращается к таблице маршрутизации.
6. Выбирает ближайшие известные контакты по XOR-расстоянию.
7. Формирует FIND_NODE_RESPONSE с тем же request_id.


При выборе ближайших контактов используется параметр K таблицы маршрутизации.

В текущей конфигурации проекта:

```text
K = 4
```

На уровне кодирования и декодирования FIND_NODE_RESPONSE предусмотрено отдельное ограничение: не более 256 контактов в одном сообщении.

Таким образом, K определяет количество ближайших контактов, используемых алгоритмом поиска, а ограничение 256 защищает обработчик сообщений от чрезмерно больших списков.





## 12. FIND_NODE_RESPONSE

FIND_NODE_RESPONSE возвращает контакты узлов, наиболее близких к запрошенному идентификатору.

Механизм реализован на этапе 2.

Направление сообщения: response.

Логическая структура payload:

```python
{
    "responder": Contact,
    "target_node_id": bytes,
    "contacts": list[Contact]
}
```

Поля:

- `responder` — контакт узла, сформировавшего ответ;
- `target_node_id` — идентификатор цели поиска;
- `contacts` — список найденных контактов.

Ответ должен содержать request_id исходного FIND_NODE_REQUEST.

При получении ответа инициатор проверяет:

1. Совпадение request_id.
2. Тип сообщения FIND_NODE_RESPONSE.
3. Корректность структуры payload.
4. Соответствие NodeID ответившего узла ожидаемому.
5. Совпадение сетевого адреса и порта ответившего узла.
6. Совпадение target_node_id с исходным запросом.
7. Допустимое количество контактов.
8. Корректность каждого Contact.
9. Отсутствие повторяющихся NodeID.
10. Сортировку контактов по XOR-расстоянию.

Некорректный ответ отклоняется.

### 12.1. Ограничения FIND_NODE_RESPONSE

При кодировании и декодировании FIND_NODE_RESPONSE выполняются следующие проверки:

- payload должен содержать строго три поля: `responder`, `target_node_id`, `contacts`;
- `responder` должен быть корректным Contact;
- `target_node_id` должен иметь тип bytes и длину ровно 32 байта;
- `contacts` должен иметь тип list;
- количество контактов не должно превышать 256;
- каждый элемент списка должен успешно преобразовываться в Contact.

При нарушении этих требований сообщение отклоняется с ошибкой PayloadError.

Проверки соответствия ответа исходному запросу и логики маршрутизации выполняются на уровне RPC и алгоритма поиска.

### 12.2. Итеративный поиск

Для поиска узлов используется алгоритм `iterative_lookup()`.

Основные параметры:

```text
K = 4
alpha = 3
```

K определяет размер используемого набора ближайших контактов в стандартной конфигурации.

alpha определяет степень параллелизма запросов поиска.

Итеративный поиск:

1. Получает начальные контакты из таблицы маршрутизации.
2. Отправляет FIND_NODE известным кандидатам.
3. Получает дополнительные контакты.
4. Проверяет их доступность и идентичность.
5. Продолжает поиск по обнаруженным кандидатам.
6. Формирует результат поиска.

При публикации DHT-записей этот механизм используется для обнаружения ближайших потенциальных хранителей.

Для репликации количество кандидатов может быть увеличено относительно стандартного K.


## 13. Работа с TCP-потоком

TCP является потоковым протоколом и не сохраняет границы сообщений.

Поэтому запрещено считать, что один вызов read() соответствует одному Frame.

В одном чтении может находиться:

- часть заголовка;
- заголовок и часть payload;
- один полный Frame;
- несколько Frame одновременно.

Для обработки используется StreamDecoder с внутренним буфером.

StreamDecoder:

1. накапливает данные до получения полного 24-байтового заголовка;
2. декодирует заголовок;
3. проверяет версию, тип и payload_length;
4. ожидает необходимое количество байтов payload;
5. формирует Frame;
6. продолжает обработку оставшихся байтов.

Таким образом, корректность протокола не зависит от того, каким образом
операционная система разбила TCP-поток на отдельные чтения.


## 14. Ограничение размера

До ожидания полного payload проверяется:

payload_length <= max_frame_payload

Значение по умолчанию:

max_frame_payload = 65536

Если:

payload_length > max_frame_payload

кадр отклоняется до ожидания или выделения памяти под заявленный payload.

Это защищает узел от неконтролируемого потребления памяти из-за чрезмерного
значения payload_length.


## 15. Обработка ошибок протокола

Нарушениями протокола считаются:

- неподдерживаемая версия;
- неизвестный тип сообщения;
- payload_length больше допустимого;
- некорректный MessagePack;
- несоответствие payload ожидаемой схеме;
- неизвестные поля;
- недопустимое направление сообщения;
- неправильный request_id ответа;
- обрыв TCP-соединения посреди заголовка или payload.

Ошибка отдельного соединения не должна останавливать TCP-сервер или весь
P2P-узел.

Если заголовок не может быть безопасно интерпретирован, соединение
закрывается без попытки сформировать ответ.

Если корректный Frame уже получен, но ошибка обнаружена на уровне payload
или направления сообщения, узел по возможности формирует ERROR.

После ошибки состояние конкретного соединения освобождается.


## 16. PING/PONG RPC

Последовательность обмена:

Node A                              Node B

   |                                  |
   | -------- PING -----------------> |
   |      request_id = X              |
   |      sender = Contact A           |
   |      timestamp_ms = T1            |
   |                                  |
   |                              Dispatcher
   |                                  |
   | <-------- PONG ----------------- |
   |      request_id = X              |
   |      responder = Contact B        |
   |      ping_timestamp_ms = T1       |
   |      responder_timestamp_ms = T2  |
   |                                  |

На этапе 1 для одного RPC используется отдельное TCP-соединение.

После получения ответа клиентская сторона закрывает соединение.

Такое решение упрощает:

- корреляцию запросов и ответов;
- управление временем ожидания;
- обработку ошибок соединения;
- реализацию первого этапа.



## 17. Проверка реализации этапа 1

Реализация этапа 1 проверяется автоматическими и ручными тестами.

Автоматически проверяются:

- encode/decode кадра;
- фиксированный заголовок размером 24 байта;
- частичный заголовок;
- частичный payload;
- несколько кадров в одном TCP-потоке;
- 100 кадров со случайной фрагментацией;
- превышение MAX_FRAME_PAYLOAD;
- неизвестная версия;
- неизвестный тип сообщения;
- обрыв соединения внутри кадра;
- некорректный request_id;
- некорректный MessagePack;
- несоответствие payload схеме;
- PING/PONG;
- ERROR;
- недопустимое направление сообщения;
- сохранение работоспособности сервера после ошибки клиента.

На момент завершения этапа 1 набор автоматических тестов содержит
36 успешно проходящих теста.

Дополнительно выполнен ручной сценарий с двумя независимыми процессами:

Node1:
127.0.0.1:9101

Node2:
127.0.0.1:9102

Node2 устанавливает соединение с Node1 как с bootstrap-узлом, отправляет
PING и получает корректный PONG с тем же request_id.

Дополнительно утилита scripts/send_ping.py позволяет вручную отправить
PING работающему узлу:

python scripts/send_ping.py --host 127.0.0.1 --port 9101

Успешный ответ содержит PONG и тот же request_id.


## 18. DHT: общая архитектура

На этапе 3 в P2P Overlay Network реализовано распределённое хранение записей на основе DHT (Distributed Hash Table — распределённой хеш-таблицы).

DHT позволяет сохранять сведения об узлах сети и получать их по 32-байтовому ключу без обращения к единому центральному серверу.

Реализация включает:

- подписанные записи NodeRecord;
- вычисление ключа записи;
- проверку владельца и цифровой подписи;
- RPC STORE и FIND_VALUE;
- репликацию на ближайших узлах;
- защиту от устаревших версий;
- ограничение срока действия записей (TTL);
- постоянное хранение записей;
- автоматическое восстановление реплик;
- переопубликование записей владельцем.

Для определения близости узлов используется метрика XOR, применяемая в Kademlia-подобной маршрутизации.

DHT работает поверх существующего протокола версии 1, TCP-транспорта и формата Frame.

## 19. Формат NodeRecord

NodeRecord — подписанная запись, содержащая сведения о конкретном P2P-узле.

Логическая структура записи:

```python
{
    "node_id": bytes,
    "identity_public_key": bytes,
    "addresses": list[str],
    "sequence_number": int,
    "issued_at": int,
    "expires_at": int,
    "signature": bytes
}
```

Назначение полей:

| Поле | Назначение |
|---|---|
| node_id | 32-байтовый идентификатор владельца |
| identity_public_key | Открытый ключ Ed25519 владельца |
| addresses | Список сетевых адресов узла |
| sequence_number | Номер версии записи |
| issued_at | Время создания записи |
| expires_at | Время окончания срока действия |
| signature | Цифровая подпись Ed25519 |

Временные метки задаются в секундах Unix time.

Номер версии `sequence_number` используется для предотвращения замены актуальной записи устаревшей.

Подпись подтверждает, что запись была создана владельцем соответствующего закрытого ключа.

### 19.1. Ограничения NodeRecord

В реализации установлены следующие ограничения:

| Параметр | Значение |
|---|---|
| Размер NodeID | 32 байта |
| Размер подписи Ed25519 | 64 байта |
| Максимальный размер сериализованной записи | 4096 байт |
| Максимальное количество адресов | 8 |
| Максимальный TTL | 300 секунд |
| Допустимое отклонение времени создания в будущее | 30 секунд |
| Диапазон sequence_number | От 0 до 2^64 − 1 |

TTL определяется формулой:

```text
TTL = expires_at - issued_at
```

Допустимое значение TTL:

```text
1 <= TTL <= 300 секунд
```

Адреса записываются в каноническом виде IP:port. Для IPv6 используется форма с квадратными скобками.

Список адресов должен быть отсортирован и не содержать повторений.

## 20. Каноническое представление и цифровая подпись

Для исключения неоднозначности при подписании NodeRecord используется строго определённое каноническое представление.

Подписываются все основные поля записи, кроме самой подписи.

Порядок полей фиксирован:

1. node_id;
2. identity_public_key;
3. addresses;
4. sequence_number;
5. issued_at;
6. expires_at.

Каноническое представление создаётся через MessagePack с сохранением указанного порядка полей.

Перед сериализованными данными добавляется доменный префикс:

```python
RECORD_DOMAIN = b"p2p-node-record-v1\x00"
```

Формирование подписываемых данных:

```python
signing_bytes = (
    RECORD_DOMAIN
    + msgpack.packb(
        [
            node_id,
            identity_public_key,
            list(addresses),
            sequence_number,
            issued_at,
            expires_at,
        ],
        use_bin_type=True,
    )
)
```

Подпись формируется закрытым ключом Ed25519 владельца.

```text
signature = Ed25519.Sign(private_key, signing_bytes)
```

При проверке используется открытый ключ из NodeRecord.

```text
Ed25519.Verify(public_key, signature, signing_bytes)
```

Изменение любого подписанного поля приводит к ошибке проверки подписи.

Доменный префикс отделяет подписи NodeRecord от подписей других типов данных протокола.

### 20.1. Пример логической записи

Следующий пример иллюстрирует структуру записи. Значения идентификатора, ключа и подписи условные и не являются действительной криптографической записью.

```python
{
    "node_id": b"<32 bytes>",
    "identity_public_key": b"<32 bytes>",
    "addresses": ["127.0.0.1:9101"],
    "sequence_number": 1,
    "issued_at": 1000000000,
    "expires_at": 1000000180,
    "signature": b"<64 bytes>"
}
```

Пример демонстрирует запись с TTL 180 секунд.

Для получения действительной записи используется функция `create_node_record()`, которая формирует и подписывает данные с помощью идентичности владельца.

## 21. Проверка NodeRecord

Перед сохранением и использованием записи выполняется проверка `validate_node_record()`.

Проверяются:

1. Корректность типов и размеров полей.
2. Длина NodeID.
3. Соответствие NodeID открытому ключу владельца.
4. Корректность и каноничность сетевых адресов.
5. Отсутствие повторяющихся адресов.
6. Диапазон номера версии.
7. Корректность временных меток.
8. Допустимое значение TTL.
9. Отсутствие истечения срока действия.
10. Отсутствие недопустимого смещения времени создания в будущее.
11. Длина цифровой подписи.
12. Подлинность подписи Ed25519.

При нарушении любого обязательного условия запись отклоняется.

При десериализации также проверяются ограничение размера, структура MessagePack и соответствие каноническому представлению.

Таким образом, удалённый узел не может произвольно изменить адреса, срок действия или номер версии чужой записи, не нарушив цифровую подпись.

## 22. DHT-ключ записи

Для NodeRecord используется 32-байтовый DHT-ключ.

Ключ вычисляется по формуле:

```python
key = SHA256(b"node:" + node_id)
```

В реализации используется функция:

```python
node_record_key(node_id)
```

Префикс `node:` отделяет пространство ключей записей узлов от потенциальных других типов объектов.

Близость DHT-ключа к идентификаторам узлов определяется XOR-расстоянием:

```text
distance(A, B) = A XOR B
```

Чем меньше XOR-расстояние, тем ближе узел к ключу.

## 23. RPC STORE

STORE предназначен для сохранения подписанной записи NodeRecord на удалённом узле DHT.

Обмен осуществляется в рамках существующего Frame версии 1.

Используются типы сообщений:

```text
STORE_REQUEST
STORE_RESPONSE
```

Инициатор:

1. Проверяет контакт получателя.
2. Проверяет NodeRecord.
3. Вычисляет DHT-ключ записи.
4. Создаёт новый request_id.
5. Кодирует STORE_REQUEST.
6. Отправляет запрос по TCP.
7. Ожидает STORE_RESPONSE.
8. Проверяет request_id, тип ответа, ключ и результат сохранения.

На принимающей стороне запрос передаётся обработчику `DHTStorage.put()`.

Хранилище проверяет запись и правила версионирования перед её сохранением.

Успешным подтверждением считается ответ, в котором поле `stored` имеет значение `true`.

При ошибке сохранения или некорректном ответе операция не считается подтверждённой.

## 24. RPC FIND_VALUE

FIND_VALUE предназначен для получения записи по DHT-ключу.

Используются типы сообщений:

```text
FIND_VALUE_REQUEST
FIND_VALUE_RESPONSE
```

При выполнении запроса:

1. Инициатор проверяет контакт получателя.
2. Проверяет длину DHT-ключа — 32 байта.
3. Формирует запрос с новым request_id.
4. Отправляет FIND_VALUE_REQUEST.
5. Получает FIND_VALUE_RESPONSE.
6. Проверяет request_id и тип ответа.
7. Проверяет совпадение возвращённого ключа с запрошенным.
8. Если запись найдена, проверяет соответствие её NodeID запрошенному DHT-ключу.

Если локальное хранилище получателя содержит действительную запись, она может быть возвращена инициатору.

Если запись отсутствует, возвращается результат без записи.

Поиск других хранителей осуществляется с использованием механизма обнаружения ближайших контактов.


### 24.1. Форматы сообщений STORE и FIND_VALUE

Все сообщения DHT используют MessagePack и передаются внутри Frame версии 1.

#### STORE_REQUEST

```python
{
    "key": bytes,
    "record": bytes
}
```

- `key` — DHT-ключ длиной 32 байта;
- `record` — сериализованная подписанная запись NodeRecord.

При декодировании проверяется соответствие ключа идентификатору владельца записи.

#### STORE_RESPONSE

```python
{
    "key": bytes,
    "stored": bool
}
```

- `key` — ключ записи, к которой относится ответ;
- `stored` — признак успешного сохранения.

#### FIND_VALUE_REQUEST

```python
{
    "key": bytes
}
```

- `key` — 32-байтовый ключ искомой записи.

#### FIND_VALUE_RESPONSE

```python
{
    "key": bytes,
    "found": bool,
    "record": bytes | None
}
```

- `key` — запрошенный DHT-ключ;
- `found` — признак наличия записи;
- `record` — сериализованная NodeRecord либо `None`.

Если `found == True`, поле `record` должно содержать байты корректной подписанной записи.

Если `found == False`, поле `record` обязательно равно `None`.

Для каждого сообщения проверяется точный набор полей. Неизвестные и отсутствующие поля приводят к отклонению payload.

Полученная NodeRecord десериализуется и проходит проверку цифровой подписи, структуры и срока действия.


## 25. Репликация NodeRecord

Для повышения отказоустойчивости запись размещается на нескольких узлах.

Параметры репликации:

```python
replication_factor = 3
required_confirmations = 2
```

Это означает:

- целевое количество реплик — 3;
- минимальное количество подтверждений для успешной публикации — 2.

Алгоритм `replicate_record()`:

1. Вычисляет DHT-ключ.
2. Проверяет полученные контакты.
3. Удаляет дубликаты по NodeID.
4. Сортирует кандидатов по XOR-расстоянию до ключа.
5. Отправляет STORE ближайшим кандидатам.
6. Учитывает успешные подтверждения.
7. При недостатке копий обращается к резервным кандидатам.
8. Возвращает результат репликации.

В результате сохраняются:

```text
key
attempted
confirmed
required
successful
confirmed_nodes
failed_nodes
```

Условие успешной публикации:

```text
confirmed >= 2
```

Условие полной репликации:

```text
confirmed >= 3
```

Успешная публикация и полная репликация — разные состояния.

При двух подтверждениях публикация считается успешной, но механизм обслуживания может продолжить восстановление третьей копии.

## 26. Отказоустойчивость и восстановление реплик

Для обслуживания записей реализован класс `ReplicaMaintenance`.

Он проверяет наличие актуальной версии записи у известных кандидатов и восстанавливает недостающие копии.

Алгоритм обслуживания:

1. Проверить действительность NodeRecord.
2. Вычислить DHT-ключ.
3. Отсортировать контакты по XOR-расстоянию.
4. Выполнить FIND_VALUE у кандидатов.
5. Подсчитать уже существующие актуальные копии.
6. Определить узлы, на которых запись отсутствует.
7. Отправить STORE для восстановления недостающих копий.
8. Подсчитать подтверждения.
9. Определить успешность восстановления.

Если удалённый узел хранит более новую версию записи, устаревшая версия на него не записывается.

Результат обслуживания содержит:

```text
checked
existing
repaired
confirmed
required
successful
fully_replicated
```

При отказе одного хранителя другие реплики могут продолжать обслуживать запросы FIND_VALUE.

После обнаружения доступных резервных узлов механизм обслуживания может восстановить необходимое количество копий.

## 27. TTL и удаление просроченных записей

Каждая запись имеет ограниченный срок действия.

Время истечения определяется полем:

```text
expires_at
```

Запись считается просроченной, если:

```python
expires_at <= current_time
```

Просроченная запись не должна возвращаться как действительная.

В `DHTStorage` предусмотрены:

- проверка срока действия при получении;
- удаление просроченных записей;
- метод `cleanup()` для очистки хранилища.

После истечения TTL данные записи могут быть удалены из активного хранилища.

При этом информация о последней принятой версии сохраняется отдельно, чтобы не допустить повторного принятия устаревшей записи.

## 28. Защита от отката версий

Для предотвращения rollback-атак используется монотонный `sequence_number`.

При сохранении новой записи выполняется сравнение с последней принятой версией.

Правила:

| Ситуация | Результат |
|---|---|
| Новый sequence_number больше сохранённого | Новая версия может быть принята |
| Новый sequence_number меньше сохранённого | Отклонение как rollback |
| Номер совпадает, содержимое идентично | Допускается повторное сохранение |
| Номер совпадает, содержимое отличается | Отклонение как конфликт |

Для защиты после перезапуска применяется постоянный журнал версий.

Журнал хранит:

- номер последней принятой версии;
- SHA-256 отпечаток сериализованной записи.

Информация о версии сохраняется отдельно от активной записи.

Поэтому истечение TTL не позволяет злоумышленнику повторно записать старую версию с меньшим номером.

Журнал версий сохраняется на диске и восстанавливается при запуске хранилища.

## 29. Постоянное хранение DHT

Хранилище `DHTStorage` использует каталог состояния узла.

Структура:

```text
state_dir/
└── dht/
    ├── <key>.json
    └── versions/
        └── <key>.json
```

Файл записи содержит сериализованные данные NodeRecord в шестнадцатеричном представлении.

Файл версии содержит сведения, необходимые для защиты от отката.

При запуске выполняется загрузка сохранённых данных.

Записи проверяются перед использованием.

Некорректные и просроченные записи не включаются в активное хранилище.

При обновлении используются временные файлы и атомарная замена через `os.replace()`.

Это снижает риск появления частично записанных файлов.

## 30. Реестр опубликованных записей

Владелец узла использует `PublishedRecordRegistry` для хранения собственных опубликованных NodeRecord.

Реестр расположен в каталоге:

```text
state_dir/published_records/
```

В реестре сохраняются записи, которые необходимо обслуживать и переопубликовывать.

Используются файлы:

```text
<key>.bin
<key>.pending
```

Назначение:

- `.bin` — сохранённая опубликованная запись;
- `.pending` — подготовленная новая версия, публикация которой ещё не завершена.

Pending-запись позволяет повторять публикацию той же подписанной версии после временной сетевой ошибки.

Если подготовленная версия истекла, создаётся следующая версия с увеличенным `sequence_number`.

Это необходимо, поскольку часть удалённых узлов уже могла получить предыдущую попытку обновления.

Реестр загружается при запуске узла.

## 31. Автоматическое обслуживание и переопубликование

При запуске узла выполняются:

```python
await self.dht_storage.load()
await self.published_registry.load()
await self.server.start()
```

После bootstrap создаётся фоновая задача обслуживания:

```python
self._maintenance_task = asyncio.create_task(
    self._maintenance_loop()
)
```

Интервал между запусками циклов обслуживания установлен:

```python
self._maintenance_interval = 5.0
```

Каждый цикл выполняет обслуживание собственных опубликованных записей.

Проверяются:

- необходимость переопубликования;
- состояние текущей версии;
- наличие незавершённого обновления;
- срок действия записи;
- наличие реплик у доступных узлов.

### 31.1. Обновление после половины TTL

Для записи вычисляется:

```python
ttl = record.expires_at - record.issued_at
```

Переопубликование становится необходимым после достижения половины TTL:

```python
now >= record.issued_at + ttl / 2
```

Новая запись:

1. Создаётся владельцем.
2. Получает увеличенный `sequence_number`.
3. Получает новые временные метки.
4. Подписывается Ed25519.
5. Сохраняется как pending.
6. Публикуется через механизм репликации.
7. После успешной публикации регистрируется как текущая версия.
8. Удаляется из pending.

Из-за периодического опроса фактический момент запуска обновления может быть позднее точной границы TTL/2.

### 31.2. Восстановление после перезапуска

После перезапуска узел загружает сохранённые записи владельца.

Если запись требует обновления, механизм обслуживания создаёт и публикует следующую версию.

Если ранее была подготовлена pending-запись, она используется для повторной попытки публикации.

Это позволяет продолжать обслуживание DHT после перезапуска без ручного восстановления списка опубликованных записей.

### 31.3. Журналирование обслуживания

В журнале используются события:

```text
dht_replication
replica_maintenance
record_refreshed
maintenance_record_refreshed
refresh_pending
```

## 33. Ограничения реализации

Текущая реализация является учебным прототипом распределённой оверлейной сети.

Основные ограничения:

- используется TCP-транспорт;
- поиск и размещение зависят от известных и обнаруженных контактов;
- количество доступных хранителей может быть меньше трёх;
- успешная публикация требует не менее двух подтверждений;
- обслуживание выполняется периодически, поэтому восстановление не мгновенное;
- фактическое переопубликование может начинаться немного позже половины TTL;
- доступность записи зависит от состояния узлов и сетевых соединений.

Псевдонимы и разрешение конфликтов подписанных алиасов относятся к необязательному расширению E3-8 и в обязательную функциональность этапа 3 не включены.

## 34. Итог этапа 3

На этапе 3 реализован механизм распределённого хранения подписанных записей узлов.

NodeRecord обеспечивает проверяемую связь между идентификатором узла, открытым ключом, сетевыми адресами, номером версии и сроком действия.

RPC STORE и FIND_VALUE обеспечивают сохранение и получение записей.

Репликация с R=3 и минимальным кворумом 2 повышает доступность данных при отказе отдельных узлов.

TTL ограничивает срок действия записей, а постоянный журнал версий предотвращает принятие устаревших данных после истечения TTL и перезапуска.

Фоновое обслуживание восстанавливает недостающие реплики и переопубликовывает записи владельца.

Таким образом, реализована программная основа DHT, необходимая для дальнейшего развития защищённой P2P Overlay Network.
