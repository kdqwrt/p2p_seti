
# Защищённая оверлейная сеть передачи данных на основе пиринговых протоколов

Программная реализация децентрализованной оверлейной сети передачи данных на основе пирингового взаимодействия узлов.

Документ описывает текущее состояние проекта: TCP-транспорт, собственный сетевой протокол, криптографическую идентификацию узлов, маршрутизацию, итеративный поиск и механизмы обработки отказов.

**Уровень реализации:** продвинутый  
**Язык:** Python  
**ОС разработки:** Windows  
**Транспорт:** TCP  
**Асинхронная модель:** `asyncio`

## Текущее состояние

В проекте реализована основа децентрализованного взаимодействия P2P-узлов с возможностью обнаружения других участников сети, проверки их доступности и выполнения поиска по распределённой таблице маршрутизации.

На данный момент реализованы:

- асинхронный TCP-сервер;
- исходящие TCP-соединения;
- собственный бинарный формат кадра;
- потоковая обработка TCP;
- сериализация payload через MessagePack;
- RPC-диспетчеризация;
- сообщения `PING`, `PONG`, `FIND_NODE_REQUEST`, `FIND_NODE_RESPONSE` и `ERROR`;
- генерация и проверка `request_id`;
- bootstrap-взаимодействие узлов;
- криптографическая идентификация на основе Ed25519;
- формирование NodeID на основе публичного ключа;
- проверка идентификационных данных `Contact`;
- таблица маршрутизации на основе принципов Kademlia;
- определение XOR-расстояния между NodeID;
- поиск ближайших известных контактов;
- итеративный поиск узлов;
- ограничение параллелизма поиска параметром `alpha`;
- проверка обнаруженных контактов через `PING/PONG`;
- обработка отказов и сетевых таймаутов;
- сбор метрик поиска и проверки контактов;
- автоматизированные эксперименты с отказоустойчивостью;
- unit-, integration- и negative-тесты.

Общая схема реализации:

```text
┌───────────────────────────────────────────────┐
│                     Node                      │
│                                               │
│      запуск / остановка / bootstrap            │
├───────────────────────────────────────────────┤
```

## Сетевой протокол

Для передачи сообщений поверх TCP используется собственное кадрирование.

Формат кадра:

```text
+---------+--------+--------+------------------+----------------+----------+
| version |  type  | flags  |    request_id    | payload_length | payload  |
+---------+--------+--------+------------------+----------------+----------+
| 1 байт  | 1 байт | 2 байта|     16 байт      |     4 байта    | variable |
+---------+--------+--------+------------------+----------------+----------+
```

Размер фиксированной части:

```text
1 + 1 + 2 + 16 + 4 = 24 байта
```

### Поля заголовка

| Поле | Размер | Назначение |
|---|---:|---|
| `version` | 1 байт | Версия протокола |
| `type` | 1 байт | Тип сообщения |
| `flags` | 2 байта | Флаги |
| `request_id` | 16 байт | Идентификатор RPC |
| `payload_length` | 4 байта | Размер payload |

Многобайтовые значения передаются в сетевом порядке байтов — **Big Endian**.

В реализации используется:

```python
HEADER_STRUCT = struct.Struct("!BBH16sI")
```

Максимальный размер полезной нагрузки по умолчанию:

```text
MAX_FRAME_PAYLOAD = 65536
```

Размер payload проверяется до ожидания полного сообщения.

Это позволяет ограничить потребление памяти при получении некорректного кадра.

## Типы сообщений

В протоколе используются следующие типы сообщений:

| Код | Сообщение | Направление | Назначение |
|---:|---|---|---|
| `0x01` | `PING` | Request | Проверка доступности |
| `0x02` | `PONG` | Response | Ответ на PING |
| `0x03` | `FIND_NODE_REQUEST` | Request | Запрос ближайших узлов |
| `0x04` | `FIND_NODE_RESPONSE` | Response | Передача списка контактов |
| `0x7F` | `ERROR` | Response / Notification | Сообщение об ошибке |

Для каждого RPC-запроса создаётся идентификатор `request_id`.

Ответ должен содержать тот же идентификатор.

Это позволяет сопоставлять запрос и соответствующий ему ответ.

Подробное описание сообщений и payload находится в [PROTOCOL.md](PROTOCOL.md).

## Сериализация

Payload сообщения сериализуется отдельно от заголовка.

```text
Python object
      │
      ▼
  MessagePack
      │
      ▼
     bytes
      │
      ▼
 Frame.payload
```

В проекте выбран **MessagePack**.

Для выбора рассматривались разные варианты:

| Характеристика | JSON | MessagePack | Protocol Buffers |
|---|:---:|:---:|:---:|
| Бинарный формат | нет | да | да |
| Поддержка `bytes` | неудобно | да | да |
| Компактность | средняя | высокая | высокая |
| Читаемость | высокая | низкая | низкая |
| Отдельная схема | не требуется | не требуется | требуется |
| Простота применения | высокая | высокая | средняя |

MessagePack используется только для сериализации.

После декодирования выполняется отдельная проверка структуры:

```text
network payload
       │
       ▼
   MessagePack
       │
       ▼
  Python object
       │
       ▼
    validation
       │
       ├──── ошибка ────► PayloadError
       │
       ▼
 validated message
```

Проверяются:

- тип корневого объекта;
- обязательные поля;
- отсутствие неизвестных полей;
- типы значений;
- допустимые диапазоны чисел;
- размеры бинарных полей;
- структура вложенных объектов.

## PING и PONG

`PING/PONG` используется для проверки доступности другого узла.

### PING

Структура:

```text
PING {
    sender: Contact,
    timestamp_ms: uint64
}
```

Пример формирования:

```python
payload = encode_ping(
    sender=self.local_contact,
    timestamp_ms=timestamp_ms,
)
```

Поле `sender` содержит Contact отправителя.

Поле `timestamp_ms` содержит временную метку отправки запроса.

### PONG

Структура:

```text
PONG {
    responder: Contact,
    ping_timestamp_ms: uint64,
    responder_timestamp_ms: uint64
}
```

Поле `responder` содержит Contact ответившего узла.

`ping_timestamp_ms` повторяет временную метку исходного PING.

`responder_timestamp_ms` содержит временную метку формирования ответа.

### Схема RPC

```text
Узел A                                      Узел B

request_id = X

    │                                         │
    │──────────── PING (X) ──────────────────►│
    │                                         │
    │                                    обработка
    │                                         │
    │◄─────────── PONG (X) ───────────────────│
    │                                         │
```

Ответ должен содержать тот же `request_id`, что и запрос.

Для нового RPC идентификатор создаётся криптографически случайно:

```python
request_id = secrets.token_bytes(16)
```

При обработке ответа проверяются:

- тип сообщения;
- соответствие `request_id`;
- структура PONG;
- корректность Contact ответившего узла;
- соответствие временной метки исходному PING.

Время RTT измеряется локально как интервал между отправкой запроса и получением корректного ответа.

## TCP Stream Decoder

TCP предоставляет поток байтов, а не отдельные сообщения.

Поэтому неверно предполагать:

```text
1 write() = 1 read() = 1 Frame
```

Например, один кадр может прийти следующим образом:

```text
Полный Frame:

┌──────────── HEADER ────────────┬────────── PAYLOAD ──────────┐
└───────────────────────────────┴──────────────────────────────┘


Полученные TCP-фрагменты:

     read #1              read #2              read #3
        │                    │                    │
        ▼                    ▼                    ▼

┌────────────┐      ┌─────────────────┐      ┌───────────────┐
│ часть      │      │ остаток header  │      │ остаток       │
│ header     │      │ + часть payload │      │ payload       │
└────────────┘      └─────────────────┘      └───────────────┘
        │                    │                    │
        └────────────────────┼────────────────────┘
                             ▼
                       StreamDecoder
                             │
                             ▼
                           Frame
```

Возможна и обратная ситуация:

```text
один read()

┌──── Frame 1 ────┬──── Frame 2 ────┬── часть Frame 3 ──┐
```

Поэтому `StreamDecoder` использует внутренний буфер и выделяет Frame только после получения всех необходимых байтов.

Алгоритм обработки:

1. Получить очередную порцию байтов.
2. Добавить данные во внутренний буфер.
3. Проверить наличие полного заголовка.
4. Декодировать заголовок.
5. Проверить размер payload.
6. Дождаться полной полезной нагрузки.
7. Сформировать Frame.
8. Продолжить обработку оставшихся байтов.

Таким образом, корректность протокола не зависит от границ отдельных TCP-чтений.

## Contact

Для представления другого узла используется структура `Contact`.

```python
@dataclass(frozen=True, slots=True)
class Contact:
    node_id: bytes
    identity_algorithm: str
    identity_public_key: bytes
    host: str
    port: int
```

Сетевые данные:

```text
Contact
│
├── node_id
├── identity_algorithm
├── identity_public_key
├── host
└── port
```

Назначение полей:

| Поле | Назначение |
|---|---|
| `node_id` | Идентификатор P2P-узла |
| `identity_algorithm` | Алгоритм идентификации |
| `identity_public_key` | Публичный ключ |
| `host` | Сетевой адрес |
| `port` | TCP-порт |

Contact используется при обмене сообщениями и в таблице маршрутизации.

Локальные метаданные, например время последней успешной проверки, не являются частью передаваемого Contact.

Они устанавливаются и обновляются локально.

## Идентификация узлов

Для криптографической идентификации используется Ed25519.

Каждый узел имеет пару ключей:

- закрытый ключ;
- публичный ключ.

Закрытый ключ должен оставаться локальным и не передаваться другим участникам сети.

Публичный ключ используется для формирования идентификатора узла.

### Формирование NodeID

Идентификатор узла вычисляется с помощью SHA-256:

```text
             Ed25519
          Public Key
               │
               ▼
             SHA-256
               │
               ▼
          256-bit NodeID
```

Логически:

```python
node_id = SHA256(public_key)
```

Это позволяет проверить соответствие заявленного NodeID представленному публичному ключу.

При этом сама проверка хеша не доказывает владение закрытым ключом. Для такого доказательства необходима криптографическая проверка, подтверждающая владение соответствующим ключом.

### Проверка Contact

При получении контакта проверяются:

1. Структура Contact.
2. Типы полей.
3. Алгоритм идентификации.
4. Размер публичного ключа.
5. Размер NodeID.
6. Соответствие NodeID публичному ключу.
7. Корректность сетевого адреса и порта.

Контакт с некорректными идентификационными данными отклоняется.

Проверка идентичности и проверка доступности являются разными операциями.

Корректный Contact может принадлежать временно недоступному узлу.

## Маршрутизация

Маршрутизация реализована на основе принципов Kademlia.

Каждый узел хранит сведения об известных участниках сети в собственной таблице маршрутизации.

Для определения близости идентификаторов используется XOR-метрика.

### XOR-расстояние

Расстояние между NodeID определяется следующим образом:

```text
distance(A, B) = A XOR B
```

Пример:

```text
Node A: 1010
Node B: 1100

XOR:    0110
```

Полученное значение интерпретируется как неотрицательное целое число.

Чем меньше расстояние, тем ближе идентификаторы в пространстве NodeID.

XOR-расстояние не связано напрямую с физическим расстоянием между компьютерами или задержкой сети.

### K-buckets

Для хранения контактов используется таблица маршрутизации с группировкой по диапазонам XOR-расстояний.

Каждый k-bucket содержит ограниченное количество контактов.

В используемой конфигурации:

```text
K = 4
```

Общий принцип:

```text
Routing Table
      │
      ├── Bucket 0
      │     └── Contacts
      │
      ├── Bucket 1
      │     └── Contacts
      │
      ├── Bucket 2
      │     └── Contacts
      │
      └── ...
```

Таблица маршрутизации позволяет:

- сохранять известные контакты;
- определять ближайшие узлы;
- выбирать кандидатов для поиска;
- обновлять сведения о доступности участников.

## Итеративный поиск узлов

Для поиска используется RPC `FIND_NODE`.

Инициатор поиска не обязан иметь непосредственное соединение с искомым узлом.

Он может последовательно получать сведения о более близких контактах от других участников сети.

### FIND_NODE_REQUEST

Запрос содержит:

```text
FIND_NODE_REQUEST {
    sender: Contact,
    target_id: bytes
}
```

`target_id` — идентификатор искомого узла.

### FIND_NODE_RESPONSE

Ответ содержит список известных контактов, наиболее близких к указанному идентификатору.

```text
FIND_NODE_RESPONSE {
    nodes: list[Contact]
}
```

### Алгоритм поиска

1. Инициатор определяет ближайшие известные контакты.
2. Выбирает кандидатов, которым ещё не отправлялся запрос.
3. Отправляет `FIND_NODE_REQUEST`.
4. Получает списки контактов.
5. Проверяет обнаруженные контакты.
6. Добавляет подходящие контакты в множество кандидатов.
7. Повторяет поиск при наличии новых подходящих кандидатов.
8. Завершает поиск при выполнении условия остановки.

### Параллелизм

Для ограничения количества одновременных запросов используется параметр `alpha`.

В текущей конфигурации:

```text
alpha = 3
```

Это позволяет выполнять несколько запросов параллельно, не опрашивая одновременно все известные узлы.

### Проверка новых контактов

Перед использованием обнаруженных контактов выполняется проверка.

```text
FIND_NODE_RESPONSE
        │
        ▼
   New Contacts
        │
        ▼
 Contact Validation
        │
        ▼
       PING
        │
   ┌────┴────┐
   │         │
  PONG     Timeout
   │         │
   ▼         ▼
Verified   Failed
 Contact   Contact
```

Если проверка неуспешна, контакт не рассматривается как подтверждённый доступный участник поиска.

Подробный алгоритм итеративного поиска описан в [ARCHITECTURE.md](ARCHITECTURE.md).

## Обработка отказов

В распределённой сети отдельные узлы могут временно или постоянно становиться недоступными.

Причины могут включать:

- остановку процесса;
- потерю сетевого соединения;
- превышение времени ожидания;
- недоступность bootstrap-узла;
- отказ промежуточного участника поиска.

Алгоритм поиска учитывает возможность отказа отдельных контактов.

### Общая схема

```text
             Lookup
                │
                ▼
        Select Candidate
                │
                ▼
           FIND_NODE
                │
        ┌───────┴───────┐
        │               │
     Response         Failure
        │               │
        ▼               ▼
   New Contacts     Mark Failed
        │               │
        └───────┬───────┘
                │
                ▼
       Continue Lookup
```

При недоступности одного кандидата поиск может продолжиться через другие известные контакты.

В результате отказ отдельного узла не обязательно приводит к завершению поиска с ошибкой.

### Восстановление узла

После повторного запуска ранее недоступный участник может снова отвечать на сетевые запросы.

Его доступность может быть подтверждена очередным PING/PONG.

Проверка поведения системы при восстановлении выполняется отдельным экспериментальным сценарием.

## Обработка ошибок

Ошибочные данные одного клиента не должны завершать работу всего узла.

Обрабатываются:

- неизвестная версия протокола;
- неизвестный тип сообщения;
- слишком большой payload;
- некорректный MessagePack;
- неправильная структура payload;
- неправильное направление RPC;
- обрыв соединения внутри кадра;
- несовпадение `request_id`;
- сетевой timeout;
- недоступность удалённого узла;
- некорректный Contact;
- неудачная проверка обнаруженного узла.

Общая схема:

```text
              Incoming data
                    │
                    ▼
              Frame validation
                    │
            ┌───────┴────────┐
            │                │
          valid            invalid
            │                │
            ▼                ▼
       Dispatcher       ProtocolError
            │                │
            ▼                ▼
         Handler        ERROR / close
                             │
                             ▼
                       server continues
```

Если заголовок уже корректно разобран и ответ можно сформировать безопасно, используется:

```text
ERROR {
    code: string,
    message: string
}
```

Пример:

```text
ERROR {
    code: "INVALID_PAYLOAD",
    message: "Payload validation failed"
}
```

В `ERROR` не должны попадать:

- traceback;
- закрытые ключи;
- секретные значения;
- локальные пути;
- полный удалённый payload.

При ошибках поиска неудачный запрос учитывается в метриках, после чего алгоритм может продолжить работу с другими кандидатами.
